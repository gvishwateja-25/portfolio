The problem

Hundreds of repositories were hosted across GitHub Enterprise. Assessing them one at a time would create repetitive manual work, inconsistent project setup, and limited visibility into overall coverage. The challenge was to create a controlled, repeatable process that could scan repositories at scale while tracking exceptions.

Scale & discovery

Find repositories, distinguish active from archived or inactive projects, and establish a reliable scope.

Repeatable execution

Standardize cloning, project identification, scanner configuration, and execution across repositories.

Operational visibility

Track outcomes centrally, identify failures, and make exceptions actionable rather than invisible.

Workflow architecture

Repositories were cloned onto the scan server. A command run on that server started the Sonar scan, and the scan results were then visible in the SonarQube dashboard.

Implementation

Repository discovery & inventory

  • Collected repository metadata from GitHub Enterprise.
  • Identified archived and active repositories.
  • Created structured inventory data for tracking and filtering.
  • Catalogued languages and build files to inform scan handling.

Automation & scan orchestration

  • Automated repository cloning and local organization.
  • Standardized SonarQube project keys and names.
  • Used source-focused scanning to reduce build dependency for the broad initial assessment.
  • Designed controlled batch execution and status logging.

Execution environment

  • Prepared a centralized Linux-based scan workspace.
  • Separated scripts, configuration, repositories, reports, and logs.
  • Addressed SSH access and GitHub Enterprise connectivity.
  • Worked toward persistent execution independent of an interactive SSH session.

Failure handling

  • Recorded scan outcomes for follow-up.
  • Investigated repository-specific failures.
  • Identified unusually large repositories for special handling.
  • Planned retries for failed or incomplete scans.

Repository landscape

Organizations

620 repositories identified, with 427 classified as active and selected for cloning based on the reported activity criteria.

Language inventory

Inventory identified 324 Java repositories and 68 JavaScript repositories among the reported language categories. Additional languages/categories were also present.

Challenges & engineering decisions

GitHub Enterprise connectivity

Resolved hostname/DNS connectivity problems and established SSH access between the scan environment and GitHub Enterprise to enable repository operations.

Large repository exception

A remaining documentation-heavy repository was reported at approximately 7.8 GB and 190,000 files. It required separate investigation due to its size and scan failure.

Controlled concurrency

Planned scan batches rather than launching all repositories concurrently, helping limit resource contention on the execution host and SonarQube.

Source-focused scan scope

Prioritized broad source analysis without requiring every repository to complete a full application build, while recognizing that build-aware analysis can provide deeper results for some codebases.

Reported results

445 repositories were included in the reported combined scanning scope.

444 scans succeeded, with one repository remaining as the reported exception.

427 active repositories were identified from the 620 repositories in organizations and cloned for the assessment.

The resulting workflow provided a repeatable process for repository discovery, scanning, status tracking, and failure follow-up.

Scan success indicates successful scanner execution; it does not mean the repositories were vulnerability-free, remediated, or passed a security quality gate. Security findings and remediation metrics are not included here because they have not been confirmed.
