AWS ECS Platform

Infrastructure automation and CI/CD for a Terraform-managed AWS development platform, with ECS on EC2, CodeDeploy blue/green orchestration, and centralized observability.

Architecture overview

Development, deployment, orchestration, and monitoring architecture.

Project overview

Designed and worked with a Terraform-managed AWS development platform supporting containerized applications, automated infrastructure provisioning, deployment orchestration, and centralized observability.

The engineering focus is repeatable infrastructure, secure deployment workflows, controlled releases, and observable cloud platforms.

Deployment workflow

  1. Source change: Application changes enter GitHub through commits and pull requests.
  2. CI: GitHub Actions coordinates build, tests, SonarQube analysis, and security checks.
  3. AWS authentication: GitHub OIDC federation assumes an authorized IAM role.
  4. Infrastructure provisioning: Terraform plan and apply manage infrastructure changes using reusable modules.
  5. Container build: Docker builds application images and publishes them to the appropriate registry.
  6. Image management: Amazon ECR stores per-service container images.
  7. Application release: Updated ECS task definitions and services use CodeDeploy blue/green orchestration for eligible public services on EC2-backed capacity.
  8. Post-deployment validation: The validation workflow covers application health, database connectivity, logs, and operational metrics.

Operational engineering

Infrastructure and access

Reusable Terraform modules, network segmentation, IAM access control, encryption, secrets management, service discovery, and load balancing support the platform.

Application data

Aurora PostgreSQL connects through RDS Proxy. FoundationDB runs on EC2 with EBS storage.

Observability

CloudWatch, OpenTelemetry, Kinesis, and Better Stack provide the architecture for centralized logs, metrics, and traces.

Release controls and rollback considerations

The platform uses CodeDeploy blue/green orchestration. In this deployment pattern, a replacement environment is validated before traffic moves from the existing version. Returning traffic to the previous version depends on the configured deployment and rollback settings.

Application rollback does not reverse a database schema change. Backward-compatible migrations must be considered separately.

Proposed controls to verify: pull-request review, build and test success, SonarQube quality gates, dependency and image scanning, Terraform plan review, authorized production approval, and post-deployment smoke tests. These are recommendations, not a claim that every gate or automatic rollback rule is configured.

Resilience and recovery scope

The infrastructure inventory describes a three-AZ VPC. This does not establish automatic failover for every application or data service. The development environment has Aurora writer instances only, with readers and reader autoscaling disabled.

ECS recovery and placement, database replication, self-managed service recovery, backup retention, and CodeDeploy automatic rollback require configuration-specific verification. No RTO, RPO, uptime, or recovery-time results are claimed.
